# 本地 AI 客服 Agents Demo

本文件记录本次讨论确认的开发 Todo，以及图谱、LAYA、QLoRA、Agent 提示词和 Mastra 代码流程的说明。目前是方案和任务清单，未勾选项目不代表已实现。

## 1. 已确认的要求

- 使用 **Mastra** 实现 Agent、工具调用和业务 Workflow。
- 运行时的模型推理全部本地部署，不依赖 OpenAI 等外部模型 API。
- 意图识别使用 **LAYA**。
- 必须包含 **QLoRA 微调**，并在客服 Agent 中使用微调后的模型。
- 必须包含 **知识库和知识图谱**。
- Demo 阶段暂不做用户权限认证。
- 知识直接入库，不设置人工审核环节；保留格式检查、去重、来源和更新删除能力。
- 订单、物流、退款、保价接口先使用模拟数据和模拟操作。

### 2.1 第一阶段 Demo 场景

Demo 用打印机 A 和墨盒 B 串起七个场景。以下结果以 2026 年 11 月 25 日的模拟数据为准。业务模块提供只读查询，资格和金额是预设样例。金额字段以分为单位。

| 场景参数 | 用户场景与样例数据 | 业务目录 |
| --- | --- | --- |
| `knowledge` | 用户问打印机 A 报 E03 怎么办，读取故障排查步骤和产品手册出处。样例同时包含产品资料、退款政策和保价政策。 | `src/business/knowledge/` |
| `order` | 按订单号查询商品、实付金额和订单状态。`DEMO-1001` 已签收，`DEMO-1002` 运输中，`DEMO-1003` 待发货。 | `src/business/orders/` |
| `logistics` | 按订单号查询运单和轨迹。`DEMO-1002` 已到配送站，`DEMO-1001` 已签收，`DEMO-1003` 尚无运单。 | `src/business/logistics/` |
| `refund` | 查看退款资格、预估金额及原因。`DEMO-1001` 的样例可退 999 元，`DEMO-1002` 的样例需先确认配送状态。 | `src/business/refunds/` |
| `price-protection` | 查看当前售价和预估差价。`DEMO-1001` 的样例可补 100 元，`DEMO-1002` 的样例没有差价。 | `src/business/price-protection/` |
| `complaint` | 用户要求投诉配送延误，流程预期登记并返回投诉编号。样例 `CMP-DEMO-001` 关联 `DEMO-1002`，当前待处理。 | `src/business/complaints/` |
| `handoff` | 用户要求人工跟进投诉，查看 `HOF-DEMO-001` 待接管记录及对话上下文。 | `src/business/handoff/` |

### 2.3 Koa 业务 Mock API

`npm run dev` 启动业务应用，默认监听 `127.0.0.1:3000`。可用 `PORT=3001 npm run dev` 指定端口。七个业务接口都只读取本地样例，供后续 Mastra Tools 调用。

| 方法 | 路径示例 | 返回数据 |
| --- | --- | --- |
| GET | `/api/v1/health` | 服务状态 |
| GET | `/api/v1/orders/DEMO-1001` | 订单详情 |
| GET | `/api/v1/orders/DEMO-1002/logistics` | 运单及物流轨迹 |
| GET | `/api/v1/orders/DEMO-1001/refund` | 退款资格及预估金额 |
| GET | `/api/v1/orders/DEMO-1001/price-protection` | 保价资格及预估差价 |
| GET | `/api/v1/knowledge/PRINTER-A-E03` | 知识条目及出处 |
| GET | `/api/v1/complaints/CMP-DEMO-001` | 投诉记录 |
| GET | `/api/v1/handoffs/HOF-DEMO-001` | 转人工记录和会话上下文 |

```bash
curl -sS http://127.0.0.1:3000/api/v1/orders/DEMO-1002/logistics
```

响应统一包含 `code`、`message` 和 `data`。查询成功时 HTTP 状态为 `200`，`code` 为 `OK`。已有订单暂无物流会返回 `404 SHIPMENT_NOT_FOUND`，订单号不存在会返回 `404 ORDER_NOT_FOUND`，错误响应的 `data` 为 `null`。已查到但不符合条件的退款或保价样例仍返回 `200`，业务资格由 `data.eligibility` 表示。

## 3. 图谱是什么，用什么实现？

### 3.1 说人话

图谱就是把“什么东西跟什么东西有什么关系”存下来，方便顺着关系查。

以打印机客服为例：

```text
打印机 A → 使用耗材 → 墨盒 B
打印机 A → 可能出现 → 故障 E03
故障 E03 → 排查方法 → 检查卡纸
检查卡纸 → 对应教程 → 文档 C
打印机 A → 适用政策 → 售后政策 D
```

用户问“打印机 A 报 E03 怎么办”，系统沿着关系找到排查方法和教程，再根据原文回答。

### 3.2 技术分工

| 技术 | 负责什么 |
| --- | --- |
| Neo4j | 保存产品、配件、故障、解决办法、政策以及它们之间的关系 |
| 本地生成模型 | 从资料中提取实体和关系，例如使用选定的 Qwen 底座 |
| TypeScript / Node.js | 在 Mastra 项目中组织提取、写入和查询代码 |
| Neo4j JavaScript 驱动 | 让 TypeScript 代码读写 Neo4j |
| Cypher | Neo4j 的查询语言，相当于普通数据库里的 SQL |

前面讨论提过用 Python 读写图谱；既然 Agent 使用 Mastra，应用侧可以直接用 TypeScript。QLoRA 训练仍可单独使用 Python 训练脚本。

### 3.3 资料怎么变成图谱？

```text
上传产品和售后资料
→ 本地模型提取实体和关系
→ 程序检查格式、统一名称、去重并记录出处
→ 写入 Neo4j
```

例如原文：

> 打印机 A 使用墨盒 B，出现 E03 时优先检查卡纸。

整理成：

```text
打印机 A, 使用耗材, 墨盒 B
打印机 A, 可能出现, 故障 E03
故障 E03, 优先排查, 卡纸
```

大模型负责提取，数据库负责保存；提取出来的关系可能出错，保留原文出处便于调试和更新。按 Demo 要求，处理后直接入库，不加入人工审核。

### 3.4 图谱和知识库怎么配合？

```text
图谱: 找到这个型号对应的故障、解决办法和资料
→ 知识库: 取出具体步骤、注意事项和原文
→ 本地模型: 组织成客服回答
```

第一版先覆盖产品、配件、故障、解决办法、政策五类实体。退款金额、保价条件、订单状态等动态信息由业务接口和代码处理。

## 4. Mastra 里面怎么接图谱？

推荐实现方式：**Neo4j 存关系，Mastra 给 Agent 挂一个查询图谱的 Tool。**

### 4.1 入库流程

```text
资料导入流程
→ 本地模型抽取关系
→ TypeScript 写入函数
→ Neo4j
```

### 4.2 查询流程

```text
用户: 打印机 A 开不了机
→ LAYA: 识别为故障咨询
→ Mastra 客服 Agent: 调用查询产品解决方案 Tool
→ Tool 通过 Neo4j 驱动查询关系
→ 返回相关故障、排查方法、资料 ID 和出处
→ 知识库返回对应资料的详细步骤
→ 微调后的本地模型组织回答
→ 返回用户
```

工具接口可以先设计为：

```text
工具名: 查询产品解决方案
输入: 产品型号、故障描述
输出: 相关故障、解决办法、资料出处
```

需要开发的三块：资料提取入图、Neo4j 查询函数、Mastra 查询工具。工具用 Mastra 的 `createTool` 封装，加入客服 Agent 的 `tools` 配置。

### 4.3 Mastra 自带 GraphRAG 和本方案有什么区别？

| 方式 | 主要作用 |
| --- | --- |
| Mastra `createGraphRAGTool` | 根据文档片段的语义关系建图，沿关联内容扩展检索 |
| Neo4j + 自定义 Mastra Tool | 明确保存和查询“产品适用政策”“故障对应办法”等业务关系 |

本 Demo 的业务图谱按第二种实现。Mastra 自带 GraphRAG 可以后续作为检索增强选项，两者不是同一个实现。

## 5. LAYA、QLoRA、Agent 提示词有什么关系？

| 组件 | 说人话 | 在哪里使用 |
| --- | --- | --- |
| LAYA | 判断用户想干什么 | 收到消息后做意图识别和分流 |
| QLoRA | 训练模型的客服能力和表达习惯 | 独立训练阶段，产出适配器 |
| 微调后的客服模型 | 理解上下文、决定是否调用工具、组织回复 | Agent 对话阶段 |
| Agent 提示词 | 告诉模型扮演谁、怎么回答、何时调用工具 | 配在 Mastra Agent 的 `instructions` 中 |
| Mastra | 把模型、提示词、工具和业务流程串起来 | 应用运行阶段 |

### 5.1 训练时

```text
客服训练数据 + 底座模型
→ QLoRA 微调
→ 生成客服适配器
→ 推理服务加载底座 + 适配器
→ 对外提供本地客服模型服务
```

QLoRA 是训练方法，不是每次对话时都执行的步骤。

### 5.2 对话时

```text
用户问题 + 最近对话
→ LAYA 识别意图
→ Mastra Agent 接收问题和意图
→ Agent 提示词 + 对话内容 + 可用工具说明
→ 微调后的客服模型
→ 直接回答 / 追问 / 调用工具
→ 工具返回知识库、图谱或业务查询结果
→ 客服模型组织回答
→ 用户
```

微调后的模型和提示词一起使用。提示词能指导表达和工具使用；退款条件、金额计算和防重复操作放在业务代码中。

## 6. Mastra 和代码上的完整流程

下面是建议的模块和文件名，属于结构示意，不表示这些文件已经存在。

```text
前端发送消息
    ↓
chat.ts: 聊天接口收到消息
    ↓
读取最近对话和当前流程状态
    ↓
laya-client.ts: 调用本地 LAYA 服务
    ↓
得到意图: 查物流 / 故障咨询 / 退款……
    ↓
router.ts: 根据意图和当前状态选择 Agent 或 Workflow
    ↓
客服 Agent: support-agent.ts
    │
    ├─ instructions ← prompts/support.ts
    │                 客服角色、语气、回答要求、工具使用规则
    │
    ├─ model ← 本地模型服务
    │          底座模型 + QLoRA 训练出的适配器
    │
    └─ tools ← tools/*.ts
               查知识库、查图谱、查订单、申请退款
    ↓
调用 agent.generate()
    ↓
Mastra 将提示词 + 对话 + 意图 + 工具说明发给本地模型
    ↓
模型判断下一步
    │
    ├─ 信息不够 → 追问用户
    │
    ├─ 可以回答 → 生成回复
    │
    └─ 需要查询或操作 → 返回工具调用请求
                         ↓
                  Mastra 执行对应 Tool
                         ↓
                  查询数据库 / 调用业务接口或 Workflow
                         ↓
                  工具结果交回本地模型
                         ↓
                  继续调用工具或生成最终回复
    ↓
chat.ts 返回结果
    ↓
前端展示
```

### 6.1 固定业务流程：退款示例

```text
router.ts 识别到退款意图
→ 启动 refund-workflow.ts
→ 收集订单号
→ 调接口查订单
→ 代码判断适用政策和退款条件
→ Agent 解释方案、询问确认
→ Workflow 提交模拟申请
→ 核实处理结果
→ Agent 回复用户
```

### 6.2 建议的代码职责

| 模块 | 职责 |
| --- | --- |
| `chat.ts` | 接收消息、读取上下文、返回回复 |
| `laya-client.ts` | 请求本地 LAYA 服务，整理意图结果 |
| `router.ts` | 根据意图、已有流程状态决定下一步 |
| `agents/support-agent.ts` | 配置客服模型、提示词和工具 |
| `prompts/support.ts` | 保存客服提示词 |
| `tools/knowledge-search.ts` | 检索知识库并返回原文出处 |
| `tools/graph-query.ts` | 查询图谱并返回结构化关系和资料 ID |
| `tools/order-query.ts` | 查询模拟订单和物流数据 |
| `services/graph-store.ts` | 管理 Neo4j 连接及读写函数 |
| `workflows/knowledge-import.ts` | 导入资料，更新向量库和图谱 |
| `workflows/refund-workflow.ts` | 管理退款步骤和流程状态 |
| `training/` | QLoRA 数据准备、训练脚本和验证配置 |

LAYA 在前面分流；提示词配在 Agent 里；QLoRA 的训练成果加载在 Agent 调用的模型服务里；Neo4j 通过 Tool 接入。

## 7. 知识、数据、业务操作怎么分工？

| 用户问题 | 处理方式 |
| --- | --- |
| 退货政策是什么？ | RAG 查询有效政策原文 |
| 这个型号适用哪个政策？ | 图谱定位关系，知识库提供详细内容 |
| 我的订单现在到哪了？ | Tool 查询业务接口 |
| 帮我申请退款 | Workflow 执行业务步骤 |
| 这单能不能退，能退就申请 | 知识库 + 业务查询 + 规则判断 + Workflow |

一个问题可以同时使用几种能力，不按“固定问题”和“非固定问题”硬分。

Embedding 与生成模型可分开部署，更换 Embedding 模型通常需要重建对应向量索引。原方案中的 PQ 如果指 Product Quantization，是向量压缩方式，等数据规模和内存压力明确后再决定是否使用。

## 8. 自学习在 Demo 中怎么做？

```text
收集未解决问题和人工处理记录
→ 记录最终答案和处理结果
→ 提取新词、新知识和新业务路径
    ├─ 新词 → 补充识别样例或检索词表
    ├─ 新知识 → 自动更新知识库和图谱
    ├─ 回复样例 → 积累下一轮 QLoRA 训练数据
    └─ 新业务路径 → 形成 Workflow 改进候选
```

知识可以按要求自动入库。把答案写入知识库不会自动让系统具备新操作能力；新业务流程仍需要对应工具、步骤和代码实现。
